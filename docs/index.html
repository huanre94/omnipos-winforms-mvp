Arquitectura General

Análisis del estado actual (As-Is) y diseño de la arquitectura objetivo (To-Be) para la separación frontend/backend.

Estado Actual (As-Is)

⚠️ El WinForms instancia directamente los repositorios. No hay separación de capas real. La lógica de negocio está distribuida entre los Forms y los Stored Procedures.
┌─────────────────────────────────────────────────────────────────┐ │ POS (WinForms) │ │ FrmLogin FrmMain FrmPayment FrmCustomer FrmSalesOrder ... │ │ Uses DevExpress UI Controls │ │ MVP pattern incompleto (solo ProductPresenter) │ └────────────────────┬────────────────────────────────────────────┘ │ Direct instantiation / static calls ┌────────────────────▼────────────────────────────────────────────┐ │ POS.DLL │ │ Repository/ ← Entity Framework 6 (Database-First, EDMX) │ │ Contracts/ ← interfaces (parcialmente implementadas) │ │ Classes/ ← DTOs y clases auxiliares │ │ Enums/ ← enumeraciones de dominio │ │ ModelPOS.edmx ← contexto EF (POSEntities) │ └────────────────────┬────────────────────────────────────────────┘ │ EF6 + Stored Procedures + XML params ┌────────────────────▼────────────────────────────────────────────┐ │ SQL Server Database │ │ Stored Procedures (SP_*) para toda la lógica transaccional │ │ Functions (FN_*) para validaciones │ └─────────────────────────────────────────────────────────────────┘

Arquitectura Objetivo (To-Be)

✅ Clean Architecture. El dominio no depende de nada externo. La API consume la capa de aplicación. El frontend solo habla con la API por HTTP/REST.

🔐 Módulo Auth

Autenticación de usuarios, validación de punto de emisión y autorización de supervisores.

Entidades involucradas

UserLoginSP_Login_Consult_ResultGlobalParameterEmissionPoint

Lógica de Negocio

  • Autenticar usuario por Username + Password + Workstation + IP.
  • Validar que el punto de emisión esté configurado y activo para la máquina.
  • Devolver parámetros globales del sistema junto al token JWT.
  • Validar autorización de supervisor (SP_Supervisor_Validate).

Reglas de Validación

  • Usuario y contraseña son requeridos.
  • IP y nombre de máquina deben coincidir con los registrados.
  • Un usuario no puede tener dos sesiones activas simultáneas en distintas cajas.

Endpoints

POST/api/auth/loginLoginRequest → LoginResponse (token + globalParams)
POST/api/auth/supervisorSupervisorAuthRequest → bool
GET/api/auth/emission-pointEmissionPointResponse

👤 Módulo Customers

CRUD de clientes, gestión de direcciones de entrega y validación de identificaciones fiscales.

Entidades

CustomerCustomerAddressIdentTypeCustomerType

Lógica de Negocio

  • Buscar cliente por cédula / RUC / pasaporte.
  • Validar tipo y formato de identificación (FN_Identification_Validate).
  • Crear o actualizar cliente (SP_Customer_Insert).
  • Gestionar múltiples direcciones de entrega por cliente.
  • Un cliente puede tener retención habilitada (UseRetention).

Reglas de Validación

  • Identificación: formato según tipo (CI = 10 dígitos, RUC = 13 dígitos).
  • Nombre, apellido, email: requeridos para factura con datos del cliente.
  • Solo un cliente con status A puede ser seleccionado.
  • Dirección de entrega: campos Address y Telephone requeridos.

Endpoints

📦 Módulo Products

Búsqueda, consulta de precios con descuentos y promociones, y soporte para productos de peso variable.

Entidades

ProductProductBarcodeInventUnitProductCategoryProductGroupSP_Product_Consult_Result

Lógica de Negocio

  • Consultar producto por código de barras o nombre.
  • Calcular precio con descuentos, promociones y modo de pago (SP_Product_Consult).
  • Soporte para productos de peso variable (balanza integrada).
  • Consultar barras adicionales (SP_ProductBarcode_Consult).

  • Si el producto requiere peso, se debe leer de la balanza antes de agregar.
  • Validar stock disponible según ubicación (LocationId).

🧾 Módulo Invoices

Creación y anulación de facturas, tickets de impresión y gestión de ventas suspendidas.

Entidades

InvoiceTableInvoiceLineInvoicePaymentSP_Invoice_Insert_ResultSalesLog

Lógica de Negocio

  • Crear factura con líneas de productos y pagos via XML (SP_Invoice_Insert).
  • Anular factura, requiere autorización de supervisor.
  • Consultar ticket de impresión (SP_InvoiceTicket_Consult).
  • Suspender y reanudar factura en progreso (SalesLog).
  • Detectar si hay una venta suspendida al abrir caja.
  • Calcular: Base IVA 0%, Base IVA X%, IVA, IRBP, Descuento.

Reglas de Validación

  • Al menos una línea de producto es requerida.
  • El monto pagado debe cubrir el total de la factura.
  • Si hay retención, debe registrarse en el mismo documento.
  • No se puede facturar si el punto de emisión no está configurado.
  • Descuento no puede exceder el subtotal del producto (HR001).

Endpoints

POST/api/invoicesCreateInvoiceRequest → InvoiceResult
GET/api/invoices/{invoiceId}/ticketList<InvoiceTicketLine>
POST/api/invoices/{invoiceId}/cancelCancelInvoiceRequest → bool
GET/api/invoices/suspendedSuspendedSaleResponse
POST/api/invoices/suspendSuspendInvoiceRequest → bool

  • Descuento dinámico según modo de pago (HR002).

🚀 Plan de Migración

Migración en 3 fases para implementar Clean Architecture desde el inicio sin crear proxies temporales.

Fases

⚡ Fase 1 — Implementar Clean Architecture con API REST

Objetivo: Construir el backend desde cero con arquitectura limpia, separando la lógica de negocio en capas bien definidas. NO hacer proxy de POS.DLL.

1.1 — Preparar la infraestructura base

POS.Domain (capa de dominio puro):

  1. Definir entidades de dominio en POS.Domain/Entities/: Customer, Invoice, Product, SalesOrder, Payment, etc.
  2. Usar Value Objects para conceptos como Identification, Money, Address.
  3. Crear interfaces de repositorio en POS.Domain/Interfaces/Repositories/.
  4. Mover enumeraciones desde POS.DLL/Enums/ a POS.Domain/Enums/.
  5. No referenciar Entity Framework ni ninguna tecnología de infraestructura.

Domain.Application (casos de uso):

  1. Crear DTOs en Domain.Application/DTOs/Requests/ y .../Responses/.
  2. Crear Application Services: AuthService, CustomerService, ProductService, InvoiceService, etc.
  3. Implementar validadores con FluentValidation en Domain.Application/Validators/.
  4. Extraer y reescribir la lógica de negocio que hoy vive en:
    • Stored Procedures → métodos en los Services.
    • Forms de WinForms → Validators.
    • Repositorios de POS.DLL → Services.

1.2 — Implementar la capa de infraestructura

POS.Infrastructure (acceso a datos y servicios externos):

  1. Migrar el modelo de Entity Framework 6 a EF Core 8 usando scaffold-dbcontext.
  2. Crear PosDbContext.cs en POS.Infrastructure/Persistence/.
  3. Implementar repositorios concretos que implementan las interfaces de POS.Domain.
  4. Envolver llamadas a Stored Procedures con FromSqlRaw / ExecuteSqlRaw.
  5. Crear servicios para periféricos en POS.Infrastructure/ExternalServices/: PrinterService, ScaleService, ScannerService.
  6. Configurar Dependency Injection en POS.Infrastructure/DependencyInjection.cs.

1.3 — Construir la API REST

POS.Api (capa de presentación HTTP):

  1. Configurar Program.cs: registrar servicios, JWT Authentication, Swagger/OpenAPI, Serilog.
  2. Crear Middleware: ErrorHandlingMiddleware y RequestLoggingMiddleware.
  3. Crear Controllers (uno por módulo): AuthController, CustomersController, ProductsController, InvoicesController, etc.
  4. Los Controllers solo llaman a los Application Services, nunca a repositorios directamente.
  5. Validar automáticamente los Requests con FluentValidation.AspNetCore.

1.4 — Manejar la transición con WinForms

Estrategia de coexistencia:

  • POS.DLL sigue funcionando para el WinForms actual.
  • La nueva API no referencia POS.DLL, es independiente.
  • Ambos sistemas apuntan a la misma base de datos.
  • Durante esta fase, no modificar el WinForms existente.
✅ Resultado: API REST funcional con Clean Architecture. WinForms sigue operando en paralelo sin cambios.
